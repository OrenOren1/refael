# EKS ALB Ingress with ACM Certificate; nginx for k3d

## Context and Problem Statement

ADR-009 selected nginx-ingress for both EKS (prod) and k3d (local) so one
Helm chart could run in both environments with no divergence. A later
submission scope note (PR #37) recorded that Terraform provisions ECR,
GitHub OIDC/IAM, and EKS only — no ACM certificate or Route53 validation —
and that the chart's nginx Ingress defaults to HTTP with an empty `certArn`.

The Helm chart still carried a dormant certificate path: `ingress.tls.certArn`
fed `service.beta.kubernetes.io/aws-load-balancer-ssl-cert`, an AWS
load-balancer *Service* annotation that nginx-ingress does not honor, while
the values comment named `alb.ingress.kubernetes.io/certificate-arn`. The
chart therefore could not terminate HTTPS with an ACM certificate in EKS,
and the local k3d demo had no need for a certificate at all.

## Decision Drivers

* Terminate public HTTPS in EKS with an ACM certificate, without an
  in-cluster TLS Secret (ACM private keys cannot be exported).
* Keep k3d/local on nginx over HTTP — no extra controller, no certificate.
* Keep one chart with an environment overlay instead of forking manifests.
* Fail fast when an EKS ingress is configured without a certificate ARN.

## Considered Options

* EKS: `alb` Ingress class managed by AWS Load Balancer Controller, with
  `alb.ingress.kubernetes.io/certificate-arn` from `ingress.tls.certArn`.
* EKS: keep `nginx` Ingress and terminate TLS at an AWS NLB/ELB via a
  Service annotation; nginx would see plain HTTP.
* EKS: keep `nginx` Ingress and mount a TLS Secret generated from a
  certificate/key pair (not available from ACM).

## Decision Outcome

Chosen option: EKS uses the `alb` Ingress class with the ACM certificate ARN
annotation; k3d keeps the `nginx` default. `helm/values-eks.yaml` is the EKS
overlay (`className: alb`, ALB scheme/target-type/HTTPS listener/redirect
annotations, `certArn` supplied per environment). `argocd/application.yaml`
loads `values.yaml` then `values-eks.yaml`, so the EKS path is GitOps-managed
while `task deploy:local` continues to use the nginx defaults. The template
emits the nginx annotation only for `className: nginx`, emits the ALB
certificate annotation whenever `certArn` is set, honors `ingress.enabled`,
and fails rendering when `className: alb` has no `certArn`.

This narrows ADR-009 for EKS: nginx remains the k3d/local choice, but EKS no
longer uses nginx-ingress.

### Consequences

* Good, because ACM terminates TLS natively at the ALB with no Secret to
  rotate or mount.
* Good, because local development keeps the existing nginx/HTTP path and
  `helm lint` covers both profiles.
* Bad, because AWS Load Balancer Controller must be installed in EKS; it is
  not provisioned by the current Terraform or Taskfile.
* Bad, because the ACM certificate itself is not created by Terraform — a
  validated certificate and its ARN are external prerequisites.
* Bad, because an ALB Ingress without `certArn` now fails Helm rendering,
  so ArgoCD will surface an error until the ARN is supplied.
* Bad, because environment parity from ADR-009 is reduced; the two
  environments now differ in ingress class and TLS behavior.

### Confirmation

`helm lint helm/ --strict` passes; `helm template` with default values
renders `ingressClassName: nginx` and no certificate annotation; rendering
with `-f helm/values-eks.yaml --set-string ingress.tls.certArn=<arn>` renders
`ingressClassName: alb` and
`alb.ingress.kubernetes.io/certificate-arn: <arn>`; rendering the EKS overlay
without an ARN fails with an explicit message.

## Pros and Cons of the Options

### ALB Ingress class with ACM certificate ARN

* Good, because ACM certificate lifecycle stays in AWS and the ALB handles
  TLS termination and HTTP-to-HTTPS redirect.
* Bad, because it adds an AWS-only controller requirement to EKS.

### nginx Ingress with NLB/ELB Service annotation

* Good, because it keeps ADR-009's nginx parity and needs no new controller.
* Bad, because the certificate annotation belongs on a LoadBalancer Service,
  not on the Ingress, so the chart would need a second resource and the
  Service type would have to change from ClusterIP.

### nginx Ingress with a TLS Secret

* Good, because TLS would terminate at the controller itself.
* Bad, because ACM does not expose the private key needed to build the
  Secret, so another certificate source would be required.

* Implementation: `helm/values-eks.yaml`, `helm/templates/ingress.yaml`,
  `helm/values.yaml`, `argocd/application.yaml`.
* Prerequisites: AWS Load Balancer Controller installed in EKS; a validated
  ACM certificate in the ALB region; `ingress.tls.certArn` set via ArgoCD
  parameter or Helm `--set-string`.
* Revisit if Terraform starts provisioning ACM/Route53, or if k3d needs TLS.
