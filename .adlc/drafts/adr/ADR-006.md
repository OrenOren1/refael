# SAST: nodejsscan + npm audit

## Context and Problem Statement

The assignment requires SAST (Static Application Security Testing) in the CI/CD pipeline that fails on critical vulnerabilities found in code. The app is a Node.js Express service. The assignment brief references the OWASP Source Code Analysis Tools list as a source for tool selection. Actual implementation pairs source SAST with dependency SCA and enforces gates as configured in CI (see below).

## Decision Drivers

* Tool must be open source / free tier
* Must integrate with GitHub Actions
* Must block the pipeline on risky findings in code/dependencies (assignment states "fail if any critical vulnerabilities are found in code")
* Node.js-specific coverage preferred
* Assignment brief explicitly references OWASP tool list

## Considered Options

* nodejsscan + npm audit (chosen)
* Semgrep OSS
* Bearer CLI
* SonarCloud free tier

## Decision Outcome

Chosen option: "nodejsscan + npm audit", because nodejsscan is the most Node.js-specific SAST tool on the OWASP list (exactly what the assignment references), is open source, and integrates with GitHub Actions. npm audit complements it by covering dependency CVEs — a separate concern from code-level issues.

Two-tool approach:
- **nodejsscan** (source SAST): scans code (e.g. `app.js`) for OWASP Top 10 patterns (injection, XSS, insecure deserialization, etc.) and the job fails if the action reports findings.
- **npm audit** (dependency SCA, not source SAST): scans `package.json`/lockfile dependency tree for known CVEs; `npm audit --audit-level=high` fails on HIGH and CRITICAL.

**Requirement mapping:** this satisfies the intent to fail on critical vulnerabilities in code (njsscan blocks on reported code findings) and is stricter in places (npm audit also blocks HIGH dependency CVEs). It differs from a literal "critical-only, source-code-only" gate because npm audit covers dependencies/severities HIGH+ rather than source code only, and Trivy separately gates fixable HIGH/CRITICAL image CVEs before push (ADR-007).

### Consequences

* Good, because nodejsscan is Node.js-specific — lower false-positive rate vs general-purpose tools on a small Express app
* Good, because npm audit is built-in (zero install overhead) and covers the full dependency tree
* Good, because both tools produce exit codes that GitHub Actions can gate on natively
* Bad, because nodejsscan has lower community activity than Semgrep — rule coverage may lag
* Bad, because npm audit reports vulnerabilities in transitive dependencies where no fix exists; overrides/triage may be needed to resolve noise

### Confirmation

Pipeline job `sast` (`.github/workflows/ci.yml`, app changes) runs `npm ci`, `npm audit --audit-level=high`, and `ajinabraham/njsscan-action@v9` (`args: "."`). Either non-zero exit fails the job.

## Pros and Cons of the Options

### Semgrep OSS
* Good, because large active community, well-maintained Node.js ruleset
* Good, because highly configurable severity gating
* Bad, because not explicitly listed on the OWASP page with Node.js support (would require justification to assignment reviewers)

### Bearer CLI
* Good, because data-flow analysis catches sensitive data leaks that pattern-matching misses
* Bad, because less known, less adoption — harder to justify to assignment reviewers

### SonarCloud
* Good, because comprehensive, trusted brand
* Bad, because requires project setup on sonarcloud.io; more overhead for a solo assignment
