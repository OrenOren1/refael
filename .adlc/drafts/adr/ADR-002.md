# Prometheus Metrics Embedded In-Process

## Context and Problem Statement

The app needs observability for Kubernetes deployment. A counter (`root_access_total`) and default Node.js runtime metrics are exposed on `GET /metrics`.

**Evidence Found**:
* `app.js` lines 2, 8–17: `prom-client` Registry, `collectDefaultMetrics`, custom Counter
* `GET /metrics` route returns Prometheus text format
* No separate metrics-sidecar config or external agent

## Decision Drivers

* Prometheus is the de-facto K8s observability standard
* Embedding in-process avoids sidecar complexity for a sample app
* Default metrics (event loop lag, GC, memory) are valuable with zero extra config

## Considered Options

* In-process prom-client (chosen)
* StatsD sidecar agent
* OpenTelemetry SDK + OTLP exporter

## Decision Outcome

Chosen option: "In-process prom-client", because it is the simplest path to Prometheus scraping in a Node.js K8s workload and matches the existing code.

### Consequences

* Good, because Prometheus scraping works out of the box with a `podAnnotations: prometheus.io/scrape: "true"` annotation
* Bad, because counter state is per-pod and resets on restart; multi-pod deployments need aggregation at query time (`sum()`)
* Bad, because mixing app logic and metrics in a single process couples the concerns

### Confirmation

`GET /metrics` returns Content-Type `text/plain; version=0.0.4`. Helm chart should add Prometheus scrape annotations.
