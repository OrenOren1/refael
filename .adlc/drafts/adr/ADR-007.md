# Trivy Image Scan Gate: HIGH+ignore-unfixed

## Context and Problem Statement

The assignment requires blocking deployment if HIGH-severity Docker image vulnerabilities are found. The pipeline builds and pushes to AWS ECR. The image must be scanned before it is pushed so a vulnerable image never reaches the registry.

## Decision Drivers

* Assignment requires blocking on HIGH+ image vulnerabilities
* Scan must run before push (not after) — a pushed vulnerable image is a live risk
* Sympera assignment used identical pattern and confirmed it works in GitHub Actions
* `ignore-unfixed` required to avoid blocking on CVEs with no available fix (would block every release permanently)

## Considered Options

* Trivy (aquasecurity/trivy-action) — chosen
* Grype (anchore/scan-action)
* AWS ECR native image scanning

## Decision Outcome

Chosen option: "Trivy", because it is the most widely adopted open-source image scanner, has a well-maintained GitHub Action, and is explicitly named in the assignment brief. Scan runs after `docker build --load` (local daemon only, no push yet) and before the push step. Pipeline fails on CRITICAL fixable CVEs; unfixed CVEs are logged but do not block.

Severity gate: `HIGH,CRITICAL` — matches assignment requirement ("block on high-severity"). `ignore-unfixed: true` prevents blocking on base-image CVEs with no patch, keeping the gate actionable.

### Consequences

* Good, because scan-before-push ensures no vulnerable image ever reaches ECR
* Good, because `ignore-unfixed: true` prevents blocking forever on base-image CVEs with no patch
* Good, because Trivy JSON output can be uploaded as a CI artifact for audit evidence
* Bad, because HIGH gate on some base images can still produce noise; `ignore-unfixed: true` mitigates this
* Bad, because Trivy pulls its DB on every run; `cache-dir` caching in Actions reduces this

### Confirmation

CI `scan` step uses `aquasecurity/trivy-action` with `exit-code: "1"`, `severity: "HIGH,CRITICAL"`, `ignore-unfixed: true`. The push step is a separate subsequent step gated on the scan step's success.

## Pros and Cons of the Options

### Grype (Anchore)
* Good, because SBOM-native, good CycloneDX output
* Bad, because less community tooling in GitHub Actions ecosystem vs Trivy

### AWS ECR Native Scanning
* Good, because zero external tool dependency
* Bad, because scan results are async (not synchronous in pipeline); cannot gate the push
