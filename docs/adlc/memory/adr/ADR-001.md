# Node.js Express Stateless Monolith

## Context and Problem Statement

The assignment requires a deployable web service for Kubernetes. The existing sample app is a single-process HTTP server with no persistent state.

**Evidence Found**:
* `app.js`: single-file Express app, no imports of DB clients, sessions, or state stores
* `package.json`: only `express` and `prom-client` as dependencies
* `process.env.PORT || 8080`: externalized port — 12-factor compliant
* No `Dockerfile`, no `docker-compose.yml` present — greenfield container layer

## Decision Drivers

* Simplicity: single-file app with no domain logic requiring service decomposition
* Assignment scope: demonstrate K8s deployment, not microservices architecture
* Stateless design enables horizontal scaling and rolling updates without session drain

## Considered Options

* Monolithic stateless Express app (chosen)
* Microservices split (overkill for scope)
* StatefulSet-backed service (inappropriate — no persistent state)

## Decision Outcome

Chosen option: "Monolithic stateless Express app", because the app has no shared state, no DB, and no domain boundaries that would justify decomposition. Kubernetes `Deployment` (not `StatefulSet`) is the correct workload type.

### Consequences

* Good, because zero-downtime rolling updates work natively with stateless pods
* Good, because horizontal pod autoscaling is trivially safe
* Bad, because Prometheus metrics are process-local — counter resets on pod restart; production use would need Pushgateway or Prometheus remote_write aggregation

### Confirmation

Confirmed by absence of DB imports, session middleware, or state stores in `app.js`. Kubernetes manifest should use `kind: Deployment`.

## More Information

**Confidence Level**: HIGH — single-file app, no ambiguity
